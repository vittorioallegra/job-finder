# job-finder: working notes for Claude

Native desktop app (Electron 45 + React 19), pnpm workspace. Full plan: `docs/plans/job-finder.md`; spec: `docs/specs/job-finder.md`.

## Commands

- Install: `pnpm setup` (runs `pnpm install`)
- Dev web renderer only: `pnpm dev` (Vite on http://localhost:5173; no preload, so settings and secrets use an in-memory bridge; open `/?demo` for made-up sample data, `?demo=off` to clear it)
- Dev desktop app: `pnpm desktop:dev`; with sample data in a separate `<userData>-demo` folder and no scheduled scans: `JOB_FINDER_DEMO=1 pnpm desktop:dev` (dataset: `packages/bridge/src/demo.ts`)
- Build desktop: `pnpm desktop:build` (output in `apps/desktop/out`)
- Package installers for this OS: `pnpm desktop:dist` (output in `apps/desktop/dist`; release steps in `docs/release.md`)
- Packaged smoke test: `JOB_FINDER_PACKAGED_APP=<executable> pnpm --filter @job-finder/desktop test:e2e:packaged`
- Release notes preview: `node scripts/release-notes.mjs --version <v> [--previous <tag>] [--assets <dir>]`
- Typecheck: `pnpm typecheck` (uses TypeScript 7 via `node node_modules/typescript7/bin/tsc`; tooling uses TypeScript 6)
- Lint: `pnpm lint` (ESLint 10 flat config, `eslint.config.mjs`)
- Format: `pnpm format` / check only: `pnpm format:check`
- Unit tests: `pnpm test` (Vitest projects: core, web, desktop, repo)
- One test file, failures only: `pnpm exec vitest run --reporter=dot apps/web/src/lib/i18n/i18n.test.ts`
- One test project: `pnpm exec vitest run --project desktop --reporter=dot`
- Electron E2E: `pnpm test:e2e:desktop` (builds first, then runs Playwright against `apps/desktop/out`; `journey.spec.ts` is the full journey, offline)
- Live ATS canary (opt-in, reads public boards): `JOB_FINDER_LIVE_CANARY=1 pnpm exec vitest run --project core --reporter=dot packages/core/src/ats/canary.test.ts`
- Record AI fixtures (live calls, manual only): `JOB_FINDER_AI_PROVIDER=<anthropic|openai|openai-compatible> JOB_FINDER_AI_MODEL=<model> [JOB_FINDER_AI_BASE_URL=<url>] [JOB_FINDER_AI_API_KEY=<key>] pnpm fixtures:record`; writes sanitized `packages/core/src/ai/fixtures/ai-<provider>.json` (the committed `ai-openai-compatible.json` is hand-made, see Conventions)
- New migration after a schema change: `pnpm --filter @job-finder/desktop db:generate --name <name>` (drizzle-kit generate; commit the new SQL and `meta/` files, never edit generated files)
- Everything: `pnpm verify`

- `packages/bridge/` typed contract between preload and renderer: zod schemas for settings, secrets, profile and IPC payloads
- `tests/repo/` repository-level conventions tests
- `docs/` specs, plans, `release.md` (installers, releases, unsigned apps), `live-smoke-test.md` (manual pass with real services), `adding-an-ats-adapter.md`

## Conventions

- Everything in the repo is English: code, comments, tests, commits, docs. Only user-facing strings are translated, through i18n keys present in both `en.json` and `it.json` (desktop main: `apps/desktop/src/main/i18n`; renderer: `apps/web/src/lib/i18n`). Key-parity tests enforce this.
- Every test file starts with the card: `// protects=...; fails_when=...; no_claim=...`. The repo test enforces it.
- UI: tokens live in `apps/web/src/styles.css` (warm editorial palette, light and dark). Screens render inside `app/AppShell.tsx` (top navigation), start with `PageHeader` and use the kit in `components/ui` (Card, Badge, ScoreRing, EmptyState, Drawer, Button with `buttonClass` for links). Fonts (Inter, Fraunces) and icons (lucide-react) are bundled, since the renderer is offline.
- Renderer never goes online: CSP is set in the main process (`src/main/security/csp.ts`). Renderer reaches the OS only through `window.jobFinder` (preload), typed by `JobFinderBridge` in packages/bridge; screens take it from `useBridge()`.
- IPC: every channel is a zod schema in `packages/bridge/src/ipc.ts`. Main checks the sender (top-level frame at the renderer origin, `security/origin.ts`) and validates the payload before any service runs. The sandboxed preload may import only `electron` and types, so it repeats channel names typed as `IpcChannel`.
- Settings are one JSON row per section (`settings.<section>`). Secrets are plain text in rows `secret.<name>` (prefixed `plain:`), not in the system keychain, so an unsigned app is never asked for a password after an update; rows from the old keychain storage read as not set. The renderer sees only set / not set. Each AI provider has its own key (`aiKeyNameFor` in bridge, read in main through `main/ai/keys.ts`); Ollama takes none.
- Protocol: the renderer loads from `app://renderer/`, served only through `resolveAppRequest` (path-traversal guard).
- Electron main/preload build as CommonJS (no `"type": "module"` in `apps/desktop`); the preload runs in the sandbox, so it may import only `electron` and types.
- CV import: text is read in `core/cv`, one structured AI call runs in the engine. A cloud provider (`isCloudAiEndpoint` in bridge) needs the user's consent, which main enforces as well as the renderer. Profile saves start a new `profile_versions` row only when scoring fields change (`scoringSnapshot`).
- AI calls run in the engine, never in the renderer. Automated tests never reach the network: they inject `createReplayFetch` (or a scripted fetch) into `createAiModel`. The API key reaches the engine only through the `ai-test` message, never the renderer.
- Only main opens SQLite. The engine asks for database work through the typed `DbCall` batches in `apps/desktop/src/engine/protocol.ts`; main executes them through drizzle's sqlite-proxy over `node:sqlite`.
- Migrations run from `apps/desktop/drizzle` in development and from `resources/drizzle` when packaged (`extraResources` in `electron-builder.yml`). A backup (`VACUUM INTO`) is written before migrating a populated database.
- Install scripts go through `allowBuilds` in `pnpm-workspace.yaml`. Allowed only when the package cannot work without it (`electron: true`, it downloads the runtime). Denied when the package works without it: `esbuild: false` (it uses its platform binary package), `electron-winstaller: false` (Windows Squirrel only; we build NSIS). Record each change in the plan's Decisions.
- `build/after-pack.mjs` is an `.mjs` file because `@electron/fuses` is ESM-only; electron-builder loads it through `afterPack`.
- The bridge is type-checked without Node types, so its tests and sources must not import `core/cv` or `core/ai` at runtime; cross-checks against core live in `apps/desktop`.
- The bundler keeps shared helpers in the engine entry, so main loads that file too. The entry starts its runtime only when `process.parentPort` exists.
- Import boundaries are enforced by ESLint: `core` and `bridge` never import apps or Electron; only `apps/desktop` imports Electron; `apps/web` never imports desktop.
- Tooling-only dependencies stay at the root; app dependencies live in the app's own `package.json`.
- E2E journey: `journey.spec.ts` sets `JOB_FINDER_FIXTURE_BASE_URL` to its own loopback server, which answers the search page, the board API, the form and the AI endpoint (`/v1/chat/completions`, configured as openai-compatible). The AI answers come from `packages/core/src/ai/fixtures/ai-openai-compatible.json`, which is hand-made (its `origin` field says so): each entry is keyed by sha256 of `POST <path>` and the exact request body. Changing a prompt, profile or job in the journey means regenerating the matching entry. Any unplanned request fails the test.
- Network: all HTTP (GET and POST) goes through `createHttpClient` (`@job-finder/core/net`), which applies the 1 req/s per-host queue and robots.txt. Tests point it at a loopback fixture server with `JOB_FINDER_FIXTURE_BASE_URL`; main passes that to the engine only when the app is not packaged and the URL is loopback (`main/engine/fixture-env.ts`). AI provider calls and the settings' model list (`core/ai/models.ts`) use plain fetch instead; Ollama on loopback is called through its native API (`ollama-ai-provider-v2`) with the chosen context as `num_ctx`; main sends each provider only its own key, the OpenAI-compatible key only to the saved server's origin, and asks Ollama only on loopback.
- JavaScript pages: the engine calls `renderPage(url)`; main renders it in the hidden loader (`main/page-loader`) with no preload, all permissions denied, downloads blocked and navigation limited to the requested origin.
- Ingestion: `core/ingest` decides what to write, the engine runs it with batched database calls through main. A company's postings close only after its complete, successful scan; a failed, cancelled or storage-broken scan closes nothing. A run can be limited to one company (a retry from the Companies screen).
- Discovery: `core/discovery` searches keyless sources through the shared HTTP client and keeps only ATS board URLs. A bot challenge is reported as `search-blocked`; the code never works around it. Keyed providers run only with their Settings toggle and a saved key: main reads the key from SecretStore and passes it to the engine in the `discover-companies` message; it never reaches the renderer or a URL. A country in the places is searched by its local and English names and its main city (`discoveryRequestFor`), since "Italia" alone finds only Italian-language pages.
- Generic careers pages: a company without a supported board is read by `core/careers`. The page is rendered through `renderPage` only when its HTML has no text. The AI lists postings and reports whether the listing is complete. Posting pages are read one hop away, on the careers host only. The AI provider and its key reach the engine in the `ingest-start` message from main; without them the scan fails as `ai-unavailable`. A model that finds no postings fails as `no-parseable-jobs`, never as a complete empty scan. Only public page text goes to the provider; no consent prompt applies.
- Scoring: `core/ranking` scores open jobs with the AI. A stored score (`job_scores`, one row per job and profile version) is reused only when its job hash, profile hash, model, prompt version and explanation language (the UI language) match. Main passes the profile's ranking fields and the key to the engine in `score-jobs`; a cloud provider needs the CV import's consent. Jobs are listed by affinity for the current profile version.
- Job filters: `core/filters` is the only place a filter becomes SQL. `places` (the profile's places) keep jobs located there and remote jobs whose scope reaches them (country name, an area containing it, worldwide); a remote job limited to other countries is out, one without a scope stays. A country or area place also needs the job's company to be based there (`companies.country`: where most of its open jobs are, refreshed at start and after each scan by `refreshCompanyCountries`, falling back to the country of the company's own web address; a company with no known country is not listed for a country), so Italy means Italian companies; a location that names only a well-known city or a US state code gets its country from `normalize/cities.ts` (stored jobs are brought along at start by `backfillLocationCountries`); a city place does not look at the company. A remote job with no scope in its location gets one from its description when that requires work authorization or citizenship in a country (`remoteScopeFromDescription`: "authorized to work in the United States", U.S. citizenship, a security clearance); stored jobs get it on the next scan. The jobs list is filtered by the profile's preferences only (`filterFromPreferences`), with no filter form; affinity scoring runs over the hard filters (every condition except new-only), visible jobs first. `job_flags` holds dismissed and viewed; a job without a row is neither, and is "new" until viewed.
- Applications: a bookmark is an application with status `bookmarked`. A job may have several applications (no unique key on `job_id`). The screens show the statuses before submitting (`bookmarked`, `preparing`, `ready`) as one "to send" group (`groupOf` in core); only those can be deleted (`isUnsent`, `applications:remove`, which also removes the documents and the PDF folder). The history records the work: starting an application writes "bookmarked" then "preparing", and each run of the documents (`startGeneration`) moves it to "preparing" and back to "ready" when something was written. Choosing another document language removes the documents written in another one. An unsent application reads "in preparation" while its documents are being written (derived from the generation store in `apps/web/src/lib/document-generation.ts`, not stored, so it cannot stick) and "to send" otherwise; jobs carry `applicationId` for that. The user does not pick a status for an unsent application: it moves by what the user does (starting to prepare, "I submitted it"), and after sending the detail offers the moves the machine allows. Moves follow `canTransition` in core; every move and note is an `application_events` row. Main's repository runs the duplicate guard before preparing: the same job or fingerprint needs two confirmations, the same company within 90 days one. The guard and `hideApplied` read `GUARD_STATUSES` and `APPLIED_STATUSES` from core.
- Documents: a tailored CV or cover letter is one structured AI call in the engine, checked by `validateDocument` (every employer, title, date, degree, institution and field equal to the profile; skill names are the profile's names or aliases; a bullet or text adds no number its source lacks). Small drifts are set right from the profile first (`repairDocument`: fixed fields copied from the profile item, bullets and sentences with foreign numbers replaced or dropped); education entries have a category (`degree` or `course`, `EDUCATION_CATEGORIES`; inferred from the title for old profiles, set in the editor and by the CV import; left out of `scoringSnapshot` so scores stay valid) and a CV with no degree gets the profile's first one; which experiences, courses, bullets and skills appear is the model's choice by relevance (the prompt asks to keep the most recent role unless unrelated; nothing is forced back in); a failed check on what is left gets one retry that names the rules; a second failure is `invalid-output`. The text follows the posting's normalized language when it is en or it, else English (`documentLanguageFor` in `core/documents/language`); the panel shows the default and lets the user pick the other. A language the user picks in the panel is saved at once on the application (`applications.document_language`, `documents:set-language`) and wins over the default. The language is stored per document (`application_documents.language`), and the PDF and its `lang` follow the stored one. No consent step applies (the user chose to generate from the application page). The documents panel shows each document as a card with Preview (the print HTML in a sandboxed iframe, `documents:preview`), Edit (fields in a dialog, dropped on cancel), Export and Show file. Saved edits pass the same validator. "Prepare application" on a job stays on the Jobs screen: it starts the application and writes both documents in the background, then offers a link to the application (`/applications?open=<id>`). Deleting asks in a dialog (`ConfirmDialog`). The PDF is the stored HTML printed by a hidden, JavaScript-free Electron window (`printToPDF`). "Save PDF" asks where to save it with the system dialog; nothing is kept in the app's data. Autofill makes a fresh PDF when the form opens, in the OS temp folder (`job-finder-uploads`). The document shows the profile's links (portfolio and so on) under the contact line, and the preview is the same HTML shown as a paper sheet on screen.
- Autofill: the form opens in its own visible window (in-memory partition, sandboxed, no preload, permissions denied, downloads only right after the user's own key or click). The app drives it through Electron's `webContents.debugger` with only the commands in `cdp.ts`'s allow list; there is no `Input` domain, so nothing presses a key or clicks. Page scripts only set values and fire input and change events. After the page loads, the fill waits up to 8 s for fields to appear, since many forms are drawn by scripts; an adapter whose posting page hides its form behind a click must set `applyUrl` to the form page (Personio: `/apply`). The app never submits; "I submitted it" moves the application to `applied`. Test pages live in `apps/desktop/src/main/autofill/fixtures/`, never live forms. The AI fallback (off unless the panel asks) maps only the fields the rules could not map: the AI answers with a profile key, a stored question or a draft (text fields only); keys resolve through the same checks as the rules, and a draft is typed only when its numbers appear in the profile. A cloud provider needs consent, which main checks before the window opens. Drafts are marked in the page and listed in the panel for review.
- Scheduler: the profile's search (a company search, then a scan) runs from main (`main/scheduler`), checked every minute, at start and on `powerMonitor` resume; a run is due when none ran or the interval passed since the newest ingest run that succeeded or failed. It starts ingestion through the ingestion service (one active run) and notifies once per run it started (scheduled or from the tray) that found new jobs for the profile. Nothing is notified under `JOB_FINDER_E2E`.
- Update check: the engine asks GitHub's latest-release endpoint through the HTTP client (fixture override applies). It does nothing when `RELEASES_REPOSITORY` is null, and main skips it under E2E without a fixture. No auto-update: the notice opens the release page only.
- Closing the window follows `app.closeBehavior`: `ask` opens the prompt in main (keep running, quit, cancel; remember writes the setting). Keep running hides the window; `before-quit` sets the flag that lets windows close without the prompt.
- Commit messages use Conventional Commits (`chore:`, `docs:`, `feat:`), no attribution lines.
